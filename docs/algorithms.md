# Алгоритмы

Реализация — в
[`src/utils/`](../../MercuryCobalt-NN/MercuryCobaldFrontend/src/utils/).
Формулы орбитальной механики и видимости переписаны один в один из эталонного
`geometry.py` (документ «Описание данных»).

## Геометрия и видимость (`geometry.ts`)

Параметры орбиты (высота, наклонение, RAAN, фазирование) переводятся в
координаты спутника на любой момент времени с учётом вращения Земли. Отсюда
же — угол возвышения спутника над наземным пунктом и проверка возможности
межспутниковой связи (по дальности и по тому, не закрывает ли Земля линию
связи). Две модели Земли сосуществуют без конфликта:

- **Базовая** — сферическая Земля, порог `min_elevation_deg` из сценария.
- **Продвинутая (WGS84)** — эллипсоид (`groundSiteEcefWgs84`) плюс реальный
  горизонт по рельефу (см. ниже); `min_elevation_deg` в этом режиме не
  участвует вовсе. Межспутниковые связи (ISL) рельеф не учитывают ни в каком
  режиме — на орбитальной высоте он не имеет физического смысла.

## Маршрутизация (`routing.ts`)

Поиск маршрута от клиентского наземного пункта до шлюза — обход в ширину
(BFS) по графу активных межспутниковых связей на конкретном отсчёте времени.
BFS находит маршрут с минимальным числом переходов и умеет объяснить, почему
маршрута нет: спутник не виден, разрыв сети, нет контакта со шлюзом или сам
шлюз недоступен (`NO_ROUTE_REASON_LABEL`). Отсутствие маршрута — не ошибка, а
штатное состояние сети в конкретный момент.

## Качество связи (`linkMetrics.ts`)

Отдельный слой поверх уже найденного маршрута — намеренно не встроен в
`routing.ts`, чтобы маршрутизация оставалась чистой топологией, а физика —
необязательной надстройкой:

- дистанция и RTT (скорость света + настраиваемая задержка коммутации на
  переход);
- качество связи: запас по углу возвышения, FSPL (потери в свободном
  пространстве) на самом длинном участке маршрута;
- робастность: число видимых спутников и дешёвая оценка числа резервных
  путей — `видимые_спутники − 1`, а не честный max-flow (слишком тяжело
  пересчитывать на каждый кадр в браузере).

## Агрегация метрик (`metrics.ts`, `constellationStats.ts`)

По серии образцов связи на всех отсчётах времени считаются: доля видимости,
доля доступности, самый длинный и суммарный перерыв, число перерывов,
средний/95-й перцентиль RTT, джиттер (среднее абсолютное изменение RTT между
соседними связанными отсчётами) и число handover'ов. Нагрузка на каждый
спутник и среднее число видимых спутников по группировке считаются один раз
за отсчёт по всем клиентам сразу (`constellationStats.ts`), а не дублируются
на каждого клиента отдельно.

## Подбор конфигурации на покрытие (`coverageOptimizer.ts`)

Ищет интервал RAAN между соседними плоскостями и фазовый сдвиг между ними —
две оси классической схемы Уокера (Walker) — максимизирующие доступность в
**наихудшем** по клиентам случае, не трогая высоту и наклонение.

Почему именно эти два параметра: горизонт расчёта — ровно сутки, а спутники
облетают Землю намного быстрее, чем она успевает провернуться под ними,
поэтому жёсткий поворот всех плоскостей на одинаковый RAAN почти не меняет
суточную статистику — это просто сдвиг фазы суточного цикла. На покрытие
реально влияет только относительный интервал RAAN между плоскостями и
относительное фазирование между ними.

Поиск двухэтапный, чтобы не подвешивать вкладку:

1. **Дешёвый скрининг** — перебор сетки (интервал RAAN × интервал фазы),
   оценка только по видимости (без маршрутизации), на прореженной сетке
   времени.
2. **Точный пересчёт** — для лучших кандидатов по видимости выполняется
   полный расчёт (вся сетка времени, реальная BFS-маршрутизация),
   ранжирование по худшей, а не средней доступности среди клиентов.

Текущая раскладка сценария всегда добавляется в точный пересчёт
дополнительно к кандидатам по сетке — иначе поиск в принципе мог бы
предложить конфигурацию хуже исходной; если она оказывается лучшей, в списке
она помечена как «текущая раскладка» с отключённой кнопкой «Применить». Цикл
поиска отдаёт управление event loop каждые ~20 кандидатов, чтобы вкладка не
подвисала. По умолчанию сетка — 24° по каждой оси
(`CoverageSearchOptions`); более мелкий шаг даёт точнее результат ценой более
долгого поиска.

## Видимость по рельефу (`src/terrain/`)

1. Фронтенд запрашивает у `terrain_api` сетку высот вокруг наземного пункта
   (см. [архитектуру](./architecture.md#терраин-бэкенд-terrain_api)).
2. Из сетки строится вычислительный (никогда не отрисовываемый) heightfield —
   `THREE.BufferGeometry` в локальной плоскости Восток/Север/Верх с центром
   на станции, в метрах, без учёта кривизны Земли (на масштабе ±30 км
   искажение на уровне сантиметров — незначимо для «грубой, правдоподобной»
   маски горизонта).
3. `THREE.Raycaster` пускает лучи по грубой сетке азимутов (каждые 5°) и
   углов места (каждый 1°, от 80° вниз до −10°), находя для каждого азимута
   максимальный угол места, при котором луч ещё пересекает рельеф — это
   `HorizonProfile`.
4. Видимость: `elevationDeg(спутник) > horizonProfile[azimuthDeg(спутник)]`.

Профиль считается один раз на пункт (рельеф статичен для расчёта) и
кэшируется в памяти на время сессии вкладки; пересчитывается только при
изменении набора наземных пунктов сценария. Модуль `three` подгружается
динамически только при первом реальном использовании продвинутого режима,
чтобы не утяжелять основной бандл для всех остальных.

Подключение к общему пайплайну — надстройка, а не переписывание:
`applyAdvancedVisibility` перезаписывает `visible` в уже посчитанном снимке
только для пунктов с готовым профилем, оставляя всё остальное (включая
пункты без профиля) нетронутым. Пока профиль не загружен, действует
консервативный откат: видимость `false`, а не молчаливая подстановка базовой
модели.

## Известные допущения и упрощения

- Расчёт пропускной способности, очередей передачи и задержки ожидания
  контакта не реализован — по постановке задачи это отдельное возможное
  расширение.
- `alt_disjoint_paths_estimate` — дешёвая оценка (`видимые_спутники − 1`), а
  не честный max-flow/Менгер; читать как верхнюю оценку, а не точное число.
- RTT/FSPL и статус линка зависят от допущений в настройках (частота,
  задержка коммутации, пороги «деградирован») — это отображаемые
  предположения, а не параметры сценария.
- Межспутниковые связи и участок маршрута между спутниками рисуются на карте
  по проекции подспутниковой точки (надир), а не по самой 3D-трассе.
- Горизонт по рельефу строится в плоской локальной плоскости, а не на полной
  сфере/эллипсоиде, и сэмплируется грубо (5° по азимуту, 1° по углу места) —
  осознанный компромисс ради скорости, а не честная 3D-трасса.
