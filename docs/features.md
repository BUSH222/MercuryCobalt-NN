# Обзор и killer-фичи

## Что решает продукт

Инженер загружает сценарий спутниковой группировки (JSON), настраивает его
(очередь запуска, ориентацию и фазирование орбитальных плоскостей, отказы
спутников) и получает ответ на главный вопрос кейса: какую долю времени
каждый наземный пункт реально может связаться со шлюзом через группировку, и
почему связь пропадает, когда пропадает.

## Killer-фичи

### 1. Всё считается в браузере

Орбитальная механика, видимость спутников над горизонтом, построение
маршрутов — весь пайплайн выполняется на TypeScript прямо в браузере, по
формулам из документа «Описание данных». Отдельного вычислительного бэкенда
нет и не нужно: слой `services/scenarioApi.ts` уже спроектирован так, что при
появлении настоящего сервера меняется реализация трёх функций, а не
компоненты интерфейса.

### 2. Подбор конфигурации на покрытие

Кнопка «Подобрать конфигурацию» ищет интервал RAAN и фазовый сдвиг между
орбитальными плоскостями (классические оси Walker-схемы), максимизирующие
доступность в **худшем** по наземным пунктам случае — ровно критерий из
постановки задачи («не менее 90% для каждого пункта»), а не среднее по всем.
Поиск двухэтапный (дешёвый скрининг по видимости → точный пересчёт с полной
BFS-маршрутизацией для лучших кандидатов), поэтому не подвешивает вкладку
даже на крупной группировке. Подробнее — [алгоритмы](./algorithms.md#подбор-конфигурации-на-покрытие).

### 3. Продвинутая видимость по реальному рельефу (WGS84)

По умолчанию видимость спутника — геометрическая, со сферической Землёй и
одним порогом угла места. «Продвинутый» режим строит настоящий локальный
горизонт вокруг каждого наземного пункта по цифровой модели рельефа
(Copernicus COP30, через OpenTopography): гора или холм на горизонте реально
закрывает низкие спутники. Это единственная часть приложения, которая делает
сетевой запрос — через отдельный лёгкий FastAPI-прокси, который прячет API-
ключ и не даёт фронтенду напрямую дёргать сторонний API. Подробнее —
[алгоритмы](./algorithms.md#видимость-по-рельефу).

### 4. Три способа увидеть одну и ту же сеть

Равнопрямоугольная и полярная азимутальная 2D-проекции рисуются одним кодом
(отличается только объект проекции), плюс отдельный вращаемый 3D-глобус
(three.js / `@react-three/fiber`, подгружается лениво) с зонами покрытия
станций и конусами видимости спутников. Один источник данных — три ракурса.

### 5. Диагностика, а не только цифра

Доступность показывается и в процентах, и в виде явной дроби по тикам
расчётной сетки («60.4% (435/720 тиков)») — по каждому наземному пункту
отдельно, не как одно усреднённое число. Диаграмма доступности привязывает
каждый разрыв связи к вызвавшему его событию (отказ спутника, недоступность
шлюза), а отдельные отметки показывают моменты смены маршрута (handover) без
потери связи. Панель «Маршрут» объясняет явную причину отсутствия маршрута
(спутник не виден, разрыв сети, недоступен шлюз), а не просто показывает
«нет связи».

### 6. Сравнение вариантов конфигурации

Любую конфигурацию можно сохранить как именованный «вариант» и сравнить
несколько вариантов в одной таблице — те же метрики, что и в панели
статистики, плюс список изменений в шапке каждого столбца. Варианты
автоматически помечаются как «штатные» или «стресс-тесты» (неполное
развёртывание, отказы, изменённая дальность ISL), чтобы не сравнивать разные
классы условий как эквивалентные.

### 7. Гибкая раскладка виджетов

Нижняя панель — не набор вкладок «одна за раз», а набор переключаемых
виджетов: любая комбинация карт, статистики, маршрута и сравнения
одновременно на экране, в сетке с перетаскиваемыми границами между панелями.

### 8. Продакшн-деплой одной командой

`docker compose up -d --build --wait` поднимает hardened Nginx-контейнер
(non-root, read-only rootfs, отброшенные capabilities, health-check) и
опциональный terrain-бэкенд отдельным контейнером — без локального Node,
Python или файла конфигурации. Подробнее — [запуск и деплой](./running.md).

## Что намеренно не реализовано

- Расчёт пропускной способности, очередей передачи и задержки ожидания
  контакта — по постановке задачи это отдельное возможное расширение;
  оценивается только геометрическая достижимость маршрута.
- Честный подсчёт числа непересекающихся резервных путей (max-flow/Менгер) —
  вместо этого используется дешёвая верхняя оценка
  `число_видимых_спутников − 1`, пересчитываемая на каждый кадр было бы
  слишком тяжело в браузере.
