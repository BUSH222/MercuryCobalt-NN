# Архитектура

## Общая картина

```
┌─────────────────────────────────────────────────────────┐
│  Браузер                                                │
│                                                         │
│   Sidebar / Settings ──▶ scenarioSlice (Redux Toolkit)  │
│                              │  overrides + baseline    │
│                              ▼                          │
│                       effectiveScenario                 │
│                              │                          │
│                              ▼                          │
│                    services/scenarioApi.ts              │
│                    (единственная граница "данны")       │
│                              │                          │
│           ┌──────────────────┼──────────────────┐       │
│           ▼                  ▼                  ▼      │
│      utils/geometry     utils/routing      utils/metrics│
│      (видимость, ECEF)  (BFS-маршрут)      (агрегация)  │
│           │                                             │
│           ▼ (только "Продвинутый" режим)                │
│   src/terrain/ (raycasting горизонта по DEM)            │
│           │                                             │
└───────────┼─────────────────────────────────────────────┘
            │ GET /api/terrain?lat=&lon=  (единственный сетевой вызов)
            ▼
   terrain_api/ (FastAPI) ──▶ OpenTopography (Copernicus COP30)
```

Почти весь продукт — SPA без сервера. Единственное исключение — терраин-
прокси для «Продвинутой» видимости, потому что реальные данные о высотах
негде взять внутри браузера.

## Слои фронтенда (`MercuryCobaldFrontend/src`)

| Слой | Назначение |
|---|---|
| `domain/` | Только TypeScript-типы: `Scenario`, `Environment`, `Plane`, `Satellite`, `GroundSite`, результаты расчёта (`Snapshot`, `Route`, метрики, `SavedVariant`). Ни строчки логики. |
| `utils/` | Вся расчётная логика: геометрия орбит и видимости, BFS-маршрутизация, метрики связи, статистика группировки, валидация сценария, поиск конфигурации на покрытие, геопроекции. |
| `mocks/` | Четыре официальных сценария-примера как статичный JSON, доступные в пустом состоянии сайдбара. |
| `services/scenarioApi.ts` | Единственная точка входа к «данным» — три асинхронных метода (`loadScenarioFromText`, `computeSeries`, `buildResultExport`, `searchCoverage`). Единственное место, которое нужно менять при подключении настоящего бэкенда. |
| `terrain/` | Локальная модель горизонта по рельефу (raycasting) — единственная часть приложения помимо `terrain_api`, которая обращается вовне. |
| `store/` | Глобальное состояние: `scenarioSlice` (Redux Toolkit + `redux-persist`) для доменных данных, `useUiStore`/`useOnboardingStore` (Zustand) для настроек интерфейса. |
| `components/` | Переиспользуемые UI-блоки, каждый в своей папке (карта, сайдбар, таймлайн, таблица сравнения, настройки, онбординг). |
| `features/` | Более крупные функциональные модули поверх компонентов (загрузка сценария, редактор конфигурации, визуализация карты, таймлайн доступности, сравнение вариантов). |

## Почему данные и UI разделены слоем `services`

`services/scenarioApi.ts` — сознательная граница: домен (`domain/`) и
компоненты опираются только на типы и на эти три-четыре асинхронных метода,
а не напрямую на `utils/geometry.ts`. Каждый метод уже сейчас имитирует
сетевую задержку (~200–350 мс), поэтому интерфейс ведёт себя так, будто
расчёт идёт на сервере, и переход на настоящий бэкенд в будущем — это замена
тела трёх функций на `fetch(...)`, без изменений в компонентах.

## Разделение состояния: Redux Toolkit + Zustand

Разделение осознанное, а не случайная смесь двух библиотек:

- **`scenarioSlice` (Redux Toolkit + `redux-persist`)** — данные: исходный
  сценарий, пользовательские изменения (`overrides`), «эффективный» сценарий
  (наложение overrides на baseline), результат последнего расчёта (`series`),
  сохранённые варианты, выбранный клиент, текущий момент времени.
  Персистится всё, кроме `effectiveScenario` (дёшево пересчитать) и `series`
  (слишком тяжёлые данные для `localStorage`).
- **`useUiStore` (Zustand)** — настройки интерфейса: свёрнут ли сайдбар,
  открытые виджеты, единицы времени, допущения RTT/FSPL. Персистится, кроме
  размеров панелей (временное удобство сессии).
- **`useOnboardingStore` (Zustand)** — один булев флаг `hasSeenTour`,
  отдельно от `useUiStore`, потому что это одноразовый флоу, а не постоянная
  настройка отображения.

Важное следствие для UX: изменение конфигурации в сайдбаре сразу обновляет
«эффективный» сценарий, но **не** пересчитывает карту/статистику само по
себе — это происходит только по кнопке «Запустить расчёт». Пользователь
всегда точно знает, какая конфигурация реально отображена, а какая ещё не
просчитана.

## Терраин-бэкенд (`terrain_api/`)

Небольшой FastAPI-сервис (Python 3.14, `uv`), единственная точка приложения,
которая ходит в интернет:

1. `GET /api/terrain?lat=&lon=` строит bbox вокруг точки (по умолчанию
   ±30 км, с поправкой `cos(lat)` на сжатие долготы к полюсам).
2. Запрашивает Copernicus COP30 у OpenTopography (API-ключ только на
   бэкенде, никогда не в бандле фронтенда).
3. Разбирает GeoTIFF через `rasterio`, даунсэмплит до сетки высот (по
   умолчанию 64×64) и отдаёт JSON вместо сырого GeoTIFF.
4. Кэширует результат на диске по округлённым координатам (`cache.py`),
   переживает пересоздание контейнера через именованный volume
   `terrain_cache`.
5. Возвращает типизированные ошибки (`invalid_api_key`, `rate_limited`,
   `upstream_error`, `invalid_request`) вместо голой 500-ки.

Ключ не обязателен для запуска сервиса — без него он поднимается нормально,
ошибка возвращается только при обращении к `/api/terrain`.

## Деплой

`Dockerfile` собирает два независимых образа из одного файла:
`runtime` (Node → статическая сборка → Nginx, non-root, read-only rootfs) и
`backend` (Python/FastAPI-прокси). `compose.yaml` поднимает оба сервиса;
`web` достаёт до `terrain` только через `nginx`-проксирование `/api/`, у
terrain-контейнера нет собственного порта, торчащего наружу. Подробности —
[запуск и деплой](./running.md).
