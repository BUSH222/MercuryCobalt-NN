Additional statistics: Here's the full rundown, grouped by why each field exists: Connectivity & path (the two things you originally asked for, plus the shape of how) - connected — reachable to any gateway right now - gateway_id, path — which gateway, and the exact node sequence, for debugging/visualizing routes - hop_count, relay_satellite_count, uses_isl — is this one bent-pipe hop or a multi-satellite relay chain - first_hop_satellite / last_hop_satellite — the serving satellites on each end, mainly so you can detect handovers later Distance → latency (your "ping" ask) - total_distance_km — raw path length - one_way_latency_ms, round_trip_latency_ms — pure speed-of-light propagation - processing_delay_ms, total_rtt_ms — same thing but with a configurable per-hop switching delay, since real satellite RTT isn't pure physics Link quality (per-hop, since one bad leg can dominate) - max_hop_km / min_hop_km / avg_hop_km — surfaces the bottleneck leg - first_hop_elevation_deg / last_hop_elevation_deg — low elevation = weaker/noisier link, more atmosphere in the way - fspl_db_bottleneck — free-space path loss on the worst leg (illustrative, depends on the frequency you assume) Robustness (how close is this client to losing service) - visible_satellite_count — handover headroom, independent of which path is chosen - alt_disjoint_paths — how many independent failures it'd take to actually cause an outage (Menger's theorem via max-flow) Series-level roll-ups (need the whole time series, not one instant) - availability, meets_target_availability — checked against the scenario's own target - mean_rtt_ms, jitter_ms — jitter as mean absolute change between connected samples - handover_count — serving-satellite changes while staying connected - outage_count, longest_outage_s — contiguous disconnected stretches Suggestions to add *Cheap, worth adding for a frontend:* - elevation_margin_deg = elevation − min_elevation_deg — how close to dropping below the visibility floor, good for an "at risk" indicator before the link actually dies - p95_rtt_ms, total_downtime_s — mean_rtt`/`longest_outage alone hide tail behavior; percentile latency and total (not just longest) downtime are more SLA-relevant - time_since_last_handover_s — path stability, useful to color-code "just switched" vs. "stable for an hour" - status enum (`"healthy" / "degraded" / "outage"`) derived from thresholds on elevation margin + RTT — one field the UI can just color directly instead of re-deriving logic in JS - serving satellite's sub-satellite point (lat/lon) — you already compute this for the position table; surfacing it alongside the client's serving-satellite choice makes a map view trivial *Constellation-wide (computed once per step across all clients, not per-client):* - per-satellite load: how many clients currently use each satellite as first/last hop — useful for a "which satellites are doing the work" heatmap, and for spotting contention if you ever add bandwidth limits - mean visible satellites across all clients — a single coverage-quality number per time step, good for a top-line chart *Skip or reimplement carefully on the frontend:* - alt_disjoint_paths is a max-flow computation — fine in Python once per client per step, but recomputing it in JS every frame for a live view could get slow on a big constellation. A cheaper proxy is visible_satellite_count - 1 (not exact, but avoids running max-flow client-side) — or only recompute it on a slower cadence (e.g. every 5th step) if you want the real number. For performance, you should do visible_satellite_count - 1 - fspl_db_bottleneck is only as meaningful as the frequency assumption behind it — worth keeping configurable/visible in the UI rather than presenting it as an absolute number.
